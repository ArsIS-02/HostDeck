# Заметки по домашней лаборатории: команды, обходные пути, что не доделано

Проект ещё в работе. Здесь собрано то, что выяснилось при развёртывании на реальных хостах, и чего нет в основной документации. Имена хостов и адреса (`redos-server`, `monitoring.test`) — из домашней лаборатории автора, подставьте свои.

## Что проверено на живом железе, а что нет

## Профили и исключения

- **Профиль хоста** (сервер / ноутбук / лаборатория) выбирается в заголовке карточки хоста. Для «сервера» пороги строгие. Для остальных часть замечаний «Внимание» становится справкой (для роли это нормально). Проблемы уровня «Проблема» профиль не смягчает.
- **Исключение** убирает конкретную проверку из итога одного хоста. Нужны причина и, по желанию, срок: после срока замечание возвращается. Проверка остаётся в списке с пометкой.
- **Соответствие, %** считается по проверкам с определённым результатом: в порядке = 1, внимание = 0,5, проблема = 0. Справочные, неприменимые, исключённые и без данных не учитываются.
- Сырой статус агента сохраняется (`raw_status`), CSV и API видят и его, и итоговый. Все изменения пишутся в журнал.

## Резервная копия базы и восстановление

На странице «Обзор» (администратору) есть карточка «Резервная копия базы»: «Скачать копию» и «Проверить копию». Проверка делает копию, открывает её отдельно и сверяет с рабочей базой (целостность SQLite и число строк в основных таблицах). Рекомендация: раз в неделю скачивать копию и хранить её вне сервера. В копии есть хэши паролей и ключей агентов, обращайтесь как с секретом.

Восстановление на сервере (RED OS, Podman):

```bash
systemctl --user stop hostdeck
V=$(podman volume inspect hostdeck-data --format '{{.Mountpoint}}')
rm -f "$V"/hostdeck.db-wal "$V"/hostdeck.db-shm
cp ~/hostdeck-ДАТА.db "$V"/hostdeck.db
systemctl --user start hostdeck
systemctl --user is-active hostdeck
```

Хосты и агенты ничего не заметят: ключи агентов лежат в той же базе.

## Основные команды

### Обновить сервер (RED OS, Podman, Quadlet)

```bash
cd ~ && rm -rf hostdeck && mkdir hostdeck && tar xzf ~/hostdeck.tgz -C ~
cd ~/hostdeck && podman build -t localhost/hostdeck:latest .
systemctl --user restart hostdeck
sleep 4; systemctl --user is-active hostdeck; curl -s http://127.0.0.1:8080/api/os-logos; echo
```

Данные лежат в томе `hostdeck-data` и не затрагиваются. Свои значки лежат в `~/hostdeck-os` и не затрагиваются.

### Установить агента на хост

Откройте «Добавить хост», скопируйте команду и выполните её на хосте. Для сервера с внутренним CA команда скачивает сертификат и скрипт, сверяет оба по отпечаткам из этой страницы и вызывает `sudo`.

Обновить агента: та же команда без токена и имени в конце.

**Обновление из веб-интерфейса.** Один раз, вручную, обновите агента готовой командой из окна «Добавить хост»: блок «Обновить уже установленного агента» уже содержит `HOSTDECK_AUTOUPDATE=1`, без токена и имени. Выключить обратно: `HOSTDECK_AUTOUPDATE=0` или `sudo hostdeck-agent set -autoupdate off`. После этого порядок такой: обновили сервер (`podman build` и `restart`), в интерфейсе у хостов появилась метка «Доступна версия», нажали «Обновить агента». Откат на хосте вручную: `sudo mv /usr/local/bin/hostdeck-agent.prev /usr/local/bin/hostdeck-agent && sudo systemctl restart hostdeck-agent` (на macOS: `launchctl kickstart -k system/local.hostdeck.agent`).

Без внутреннего CA обновление можно сделать короткой командой:

```bash
curl -fsSL https://СЕРВЕР/install.sh | sudo bash -s --
```

Удалить: `sudo ./scripts/uninstall.sh` на хосте, затем удалить хост в интерфейсе.

### Диагностика агента

```bash
# macOS
tail -n 50 /var/log/hostdeck-agent.log
sudo launchctl print system/local.hostdeck.agent
# Linux
journalctl -u hostdeck-agent -n 50
# что собирает агент прямо сейчас
sudo /usr/local/bin/hostdeck-agent collect
```

### Свои значки ОС

Положите `apple.svg` и `tux.svg` (или `.png`) в `~/hostdeck-os`, затем один раз смонтируйте каталог:

```bash
cat > ~/.config/containers/systemd/hostdeck.container.d/os.conf <<'EOF'
[Container]
Volume=/home/redos/hostdeck-os:/srv/app/static/os:ro,Z
EOF
systemctl --user daemon-reload && systemctl --user restart hostdeck
```

Файлы должны быть доступны на чтение (`chmod 644`). Логотипы Apple и Linux — товарные знаки и маскот соответственно; берите их с официальных страниц и соблюдайте условия использования.

## Обходные пути и подводные камни

**Podman и `/run/secrets`.** С `ReadOnly=true` секрет не монтируется («make mountpoint /run/secrets/admin_pw: read-only file system»). Поэтому в юните `ReadOnly` не используется.

**Сеть Caddy.** Юнит подключён к сети `n8n-net`, где работает контейнер `caddy`. Конфиг Caddy генерируется из `~/homelab-services/services.yaml` командой `ZONE=apps.monitoring.test ./generate.py`; живой файл — `~/n8n-docker-caddy/caddy_config/Caddyfile.apps` (путь `caddy_import` в README того проекта устарел).

**Сертификат внутреннего CA для установки агентов.** Корень Caddy кладётся в `~/hostdeck-ca/ca.pem` и монтируется в контейнер drop-in'ом `ca.conf` (см. `docs/podman.md`, раздел 3a). Файл должен быть читаем внутри контейнера: `chmod 644 ~/hostdeck-ca/ca.pem`, иначе `/ca.pem` отдаёт 404, потому что сервис работает не от root.

**Панель Atrium и красная лампочка у HostDeck.** Atrium проверяет бэкенд со своей стороны. HostDeck доступен Caddy по имени контейнера (`reverse_proxy http://hostdeck:8080`, сеть `n8n-net`), а Atrium в `n8n-net` нет. Поэтому «Проверить бэкенд» пишет «нет ответа», хотя сайт работает. В `services.yaml` для этого сервиса должно стоять `backend: hostdeck:8080`, `scheme: http`; не вписывайте в форму `имя.monitoring.test:8080`, иначе после перезагрузки Caddy сайт перестанет открываться.

Чтобы лампочка стала зелёной без публикации порта наружу, контейнер Atrium пересоздают с сетью `n8n-net` (в сетевом режиме `pasta` подключить вторую сеть на лету нельзя, `podman network connect` отказывает). Данные Atrium лежат в каталогах хоста, поэтому пересоздание безопасно:

```bash
podman stop atrium && podman rename atrium atrium-old
podman run -d --name atrium --restart=always --network n8n-net -p 5000:5000 -e ZONE=apps.monitoring.test \
  -v /home/redos/homelab-services:/data:z -v /home/redos/n8n-docker-caddy/caddy_config:/caddy:z localhost/atrium:v1.0.0
# откат: podman rm -f atrium && podman rename atrium-old atrium && podman start atrium
```

**Системный `curl` macOS игнорирует `--cacert`** (SecureTransport). Поэтому установщик не полагается на проверку канала: подлинность CA и скрипта подтверждают отпечатки в команде, суммы агентов вшиты в скрипт, а токен отправляет сам агент с проверкой по CA.

**DNS на Mac.** Если домашний DNS не отвечает, а публичные резолверы не знают зону `.test`, добавьте запись в `/etc/hosts`: `192.168.1.137 hostdeck.apps.monitoring.test`.

**Антивирус на Mac (Kaspersky)** блокирует сайты лаборатории: «Цепочка сертификатов не является завершённой». Корень Caddy нужно добавить в связку ключей и пометить «Всегда доверять» (двойной щелчок по `.pem` → «Связка ключей»). Команда `sudo security add-trusted-cert` из терминала может отвечать `no user interaction was possible`; тогда делайте через графический интерфейс. Если не помогло, антивирус ведёт свой список доверия, добавьте домен в его исключения. Точные названия пунктов зависят от версии.

**Mac mini в Rosetta.** `uname -m` может показать `x86_64` под Rosetta-терминалом. Установщик выбирает архитектуру по `uname -m`; на M-серии лучше запускать терминал нативно.

**`dnf check-update` долгий.** Проверка обновлений пакетов на Linux идёт в фоне, первый отчёт показывает «Проверка выполняется».

**Тест консоли иногда нестабилен.** В `tests/ui_check.py` шаг «команда выполнена, вывод отображён» изредка не проходил в песочнице. Причину не нашли; если консоль на реальном хосте теряет ввод, это первое, что стоит исследовать.

**Проверки соответствия: что стоит знать.**
- Часть проверок macOS — эвристики: «Удалённое управление» (процесс ARDAgent) и «XProtect» (дата файлов набора). Если показывают не то, что в Системных настройках, сверьте командами из подсказки и сообщите.
- «Открытые порты» без списка разрешённых только показывают, что открыто. Список задаётся в `/etc/hostdeck/agent.json` (`"allowed_ports": [22, 443]`) и применяется после перезапуска агента. Интерфейса для этого пока нет.
- «Пересылка журналов» проверяет настройку и работающую службу, а не доставку. Что сообщения доходят, смотрите в Graylog или Wazuh.
- Часть проверок на типичном хосте будет жёлтой (отдельный `/tmp`, контроль целостности, политика паролей): это не поломка, а отсутствие рекомендованной настройки. Механизма «принятый риск» с причиной и сроком пока нет.
- Новые проверки появляются после обновления агента до 0.4.0 или новее.
